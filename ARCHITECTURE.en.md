# Surgical Dev architecture

**Status date:** 2026-11-13. This document describes the implemented package only.
Test and host evidence is in [VALIDATION.md](VALIDATION.md); Pi operation is in
[Pi setup](adapters/pi/SETUP.md).

## 1. Purpose

Surgical Dev turns a development goal into a confirmed acceptance draft, then runs
one Worker through planned Todos, real project checks, one fresh independent review,
and bounded repair. The package has two layers:

- **Portable Skills** (`skills/*/SKILL.md`): six instruction sets that an Agent Skills
  host can load. They guide work and enforce nothing by themselves.
- **Pi extension** (`adapters/pi/`): the only implemented runtime controller. It owns
  confirmation, state, budgets, subprocess launches, snapshot binding and the terminal
  state of a run.

## 2. Components

| Component | Location | Responsibility |
|---|---|---|
| Skills | `skills/` | Six methods: entry, feature, bug, engineering discipline, verification and manual learning |
| Role charters | `roles/` | Worker and Verifier. Pi reads `roles/worker.md` and `roles/verifier.md` at run time |
| Record contracts | `contracts/` | Basic JSON Schemas for task and review shapes and state rules. The Pi loop does not validate against them |
| Templates | `templates/` | Markdown goal, work item, review request, review report and lesson templates |
| Pi extension | `adapters/pi/` | Commands, Goal Specification, Todo DAG, check runner, reviewer launcher, state and learning stores |
| Bundled references | `skills/*/references/` | Copies of canonical Markdown so each installed Skill is self-contained. Generated by `scripts/sync_skill_references.py` and checked by tests |

Pi modules: `extension.mjs` (commands and tools), `loop.mjs` (run controller),
`spec.mjs` (Goal Specification validation and digest), `confirmation.mjs` (exact
confirmation phrases), `persist.mjs` and `repository-store.mjs` (revision-checked
state writes), `process.mjs` (Git and subprocess helpers, snapshot capture),
`learning.mjs`, `status.mjs` and `tool-schemas.mjs`.

## 3. Pi single-workstream lifecycle

1. **Discuss.** `/surgical <goal>` starts a read-only discussion. The agent asks only
   material questions and shows a full draft: goal, scope, non-goals, constraints and
   numbered acceptance criteria (AC). `/surgical import <file>` is the advanced path
   for a requirements document. Source files are not changed here.
2. **Confirm.** A Goal Specification is confirmed only by a recorded source:
   `USER_COMMAND:/surgical confirm` or `USER_INPUT:confirm-and-start` (the user's own
   message `confirm and start` or `确认，开始`). Runtime tools cannot supply consent.
   The digest of the displayed revision is checked before a run starts.
3. **Plan.** The Worker reads the repository and calls `surgical_plan` with a Todo
   dependency graph. The graph must be acyclic, and every original AC must be covered
   exactly once.
4. **Implement and check.** One persistent Worker session implements the current Todo.
   Project checks come from `.surgical-dev.json` as argument arrays and run without a
   shell. Only the controller marks a Todo done, and only after its checks pass.
   Failed checks return to the same session.
5. **Review.** After all Todos are done, the controller captures a Git snapshot using
   a temporary index, so the user's index is unchanged. It starts a fresh `pi` process
   in a detached worktree with `read,grep,find,ls` tools only, with sessions,
   extensions, MCP, skills and context files disabled. The reviewer returns per-AC
   PASS, CHANGES_REQUIRED or BLOCKED. Path:line evidence is validated against the
   snapshot.
6. **Repair.** Findings return to the same Worker as an additive repair Todo, followed
   by fresh checks and a fresh review. Repair cycles are bounded by
   `max_review_repair_cycles` (default 2).
7. **Stop.** Terminal states are `PR_READY`, `BLOCKED`, `ESCALATED`, `CANCELLED` and
   `TIMED_OUT`. `PR_READY` binds the final evidence to the snapshot. It is not a push,
   pull request, merge or release. If `.surgical-dev.json` changes during a run, the
   run stops as `BLOCKED`.

## 4. Invariants enforced by the Pi controller

- Confirmed scope and ACs are fixed by the controller. The Worker prompt forbids
  changing them, removing original Todos, weakening checks or editing
  `.surgical-dev.json`. The policy digest check enforces the file rule.
- Turn, check and review budgets are cumulative, and a total run deadline applies.
  Limits are checked before each subprocess spawn.
- A repository-level lock prevents concurrent loops. State changes use revision-checked
  writes, and a persistence failure is reported rather than ignored.
- The Worker and reviewer run in separate processes with different session IDs. These
  IDs are references to verify, not authenticated identities.
- Evidence is version-bound. Reviews and `PR_READY` records carry the snapshot head and
  tree.
- Unreported token or cost totals are `UNKNOWN`, never zero.

## 5. Learning (local and advisory)

Learning records live at `<git-common-dir>/surgical-dev/learning.json`, outside the
source snapshot. Each normalized failure signature keeps a label and a count. Secrets
are redacted before storage, and at most 50 records are retained. On the second
occurrence, the Worker's repair feedback gets one `LEARNING (advisory, not a gate)` line.
`/surgical lessons` lists the latest 20 records.

Learning cannot change ACs, checks, scope, budgets or a review verdict, and it cannot
block `PR_READY`. Storage errors become warnings. There is no lesson lifecycle, no
lesson tool, no promotion step, and no sync between clones. The manual method is in
[learn-from-failures](skills/learn-from-failures/SKILL.md) and
[references/learning.md](references/learning.md).

## 6. Host support

| Host | Implemented here |
|---|---|
| Pi 1.5.2+ | Full single-workstream loop. Exercised with real Pi processes and a deterministic local model |
| Codex | Skills, setup guidance and an optional reviewer agent file. No controller |
| Claude Code | Skills and setup guidance. No controller; the host must supply a fresh reviewer |
| Other Agent Skills hosts | Skill format only; independent review must be arranged by the host |

Real-model behavior has not been evaluated. See [validation](VALIDATION.md) for the
exact coverage and limits.

## 7. Portable Skill layer

Each Skill is a `SKILL.md` with `name` and a `description` that begins with "Use when",
plus a `## Return` section listing what to report. A Skill is a procedure. It does not
grant permission, create agents or change a host's approval settings. The
`skills/*/references/` copies must match their canonical sources; tests check this.

## 8. Not implemented

- Multi-Worker scheduling, peer workstreams, shared-resource claims and cross-workstream
  integration acceptance. Pi runs one Worker through one sequence of Todos.
- Controller-dispatched temporary subagents.
- Durable crash recovery and automatic resume. Interrupted runs are not resumed
  automatically. `/surgical stop` cancels an active run.
- Push, draft pull request, CI reconciliation, merge, tag, package publication,
  deployment and rollback. No extension code performs these actions.
- Product Scout, outcome evaluation, incident handling and any release role or Skill.
- A learning lesson lifecycle, promotion, a lesson tool and cross-clone sync.
- A cross-record validator for the JSON contracts. Schemas cover basic shapes only.
- Real-model evaluation, long-duration runs, and controllers for Codex or Claude Code.
- Enforced sandboxing. The reviewer's read-only tool list is not an OS sandbox.
